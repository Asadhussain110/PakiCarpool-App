- **No missing or renamed table/column was found** between the 15 current EF entity models, the final snapshot, and raw SQL in `RideSearchQuery`, `SeatCapacityQuery`, `LiveLocationQuery`, `RideAnalyticsQuery`, `ReportQuery`, and `RideRepository.UpsertDriverLocationAsync`. # 4. Bugs/risks

## API, authorization, and backend behavior

### Critical/security

- **Admin TOTP can be bypassed with the step-one token.** `AdminLoginAsync` returns a partial JWT carrying the Admin role and `adminStep1`; `AdminPolicy` checks only the role, and `AdminController` requires only that policy. The token also carries the version accepted by `OnTokenValidated`. No rule requires TOTP completion or rejects `adminStep1` on admin routes (`AuthService.cs:699-727`; `JwtHelper.cs:90-117`; `RolePolicy.cs:27-43`; `AdminController.cs:18-20`; `Program.cs:283-308`).
- **Driver liveness-pending tokens are accepted as ordinary Driver tokens.** `DriverController` requires only `DriverPolicy`, which checks the role but does not exclude `livenessPending`. Except for `PostRideAsync`, driver operations do not recheck liveness. The hub is merely `[Authorize]` and also accepts pending tokens for location/chat/group operations (`DriverController.cs:16-18`; `RolePolicy.cs:29-43`; `DriverService.cs`; `PakiCarpoolHub.cs:19-20,90-146`).
- **Server-side liveness approval trusts forgeable client booleans.** Any three distinct supported prompts with `Passed=true` satisfy `IsCompleteOnDevicePass`; the nonce is not bound to server-selected prompts or a server-verifiable biometric/attestation result. A modified client can submit three passing values and receive a full JWT (`LivenessService.cs:179-193,219-237`; `DriverDtos.cs:167-190`).
- **Fresh driver logins do not receive a refresh-token cookie.** Password/OAuth driver login returns only a partial token. Automatic and manual liveness approval return only an access token; neither path calls `IssueTokenPairAsync` or sets a refresh cookie. The mobile app consequently has nothing to rotate after the 15-minute driver token expires (`AuthService.cs:241-246,791-828`; `LivenessService.cs:179-193,257-269`; `LivenessController.cs:45-61`; `AuthController.cs:220-229`).
- **Post-ride liveness refresh enforcement is bypassed on the real client path.** `AuthController.Refresh` depends on `HttpContext.User`/`iat`, but the Flutter `_refreshDio` sends only the refresh cookie and no bearer token, so `GetIssuedAtFromClaims` receives no principal and returns null. `JwtHelper.GenerateToken` also does not explicitly add an `iat` claim (`AuthController.cs:79-99`; `AuthService.cs:272-288,884-894`; `JwtHelper.cs:151-164`; `api_client.dart:286-301`).
- **Suspended users' existing access is not reliably revoked.** Blocking/trust suspension revokes refresh tokens but not the current access-token `jti`; `RevokeTokenAsync` has no caller. Passenger/driver token validation does not recheck `IsActive`/`IsSuspended`, and many endpoints/services do not either. Already-connected SignalR users likewise have no per-call suspension check (`AdminService.cs:148-164,479-507`; `TrustService.cs:108-188`; `JwtMiddleware.cs:55-93`; `TokenRevocationService.cs:24-45`; `PakiCarpoolHub.cs`).
- **Resolved (backlog 15): backend password policy now matches the Flutter policy.** Registration, password reset, and admin password reset enforce 8–128 characters plus uppercase, lowercase, digit, and symbol server-side through the shared `PasswordPolicy` helper, with a 400 message listing every missing requirement; login never re-checks composition, so older passwords keep working (`AuthDtos.cs`; `AuthService.cs`; `PasswordPolicy.cs`).
- **Resolved (backlog 15): email OTP now has per-account attempt limiting, resend, and SMTP-failure recovery.** Verification counts wrong codes per account (3 wrong → 15-minute lock, current code invalidated, constant-time hash comparison), `POST /api/v1/auth/verify-email/resend` enforces a 60-second cooldown and 3 resends per 15-minute window per account with enumeration-safe identical responses, and an SMTP failure during registration rolls back the newly created unverified user so re-registering works (`AuthService.cs`; `UserRepository.cs`; `AuthController.cs`; migration `20261125110039_AddEmailOtpAttemptAndResendLimits`, created but not applied).
- **Refresh rotation is not atomic.** The old token is read/revoked in one operation and the replacement is created in another, with no conditional consume or token-family replay handling; concurrent uses of the same old token can both pass the initial check (`AuthService.cs:257-295,896-934`; `UserRepository.cs:498-517`).
- **Token expiry is effectively five minutes longer than configured.** Both custom JWT validation and ASP.NET JWT Bearer use `ClockSkew = 5 minutes`, including for the 10-minute admin token and partial tokens (`Program.cs:258-268`; `JwtMiddleware.cs:62-72`; `JwtHelper.cs:124-143`). The admin UI expiring earlier does not make the API token invalid.
- **Resolved (backlog 8): admin bootstrap now uses `ADMIN_SEED_TOKEN`.** A one-time `POST /api/v1/auth/admin/bootstrap` path accepts the seed only through `X-Admin-Seed-Token`, compares SHA-256 token hashes in constant time, and atomically creates the first admin with an encrypted, verified TOTP secret. It returns the TOTP enrollment details once, never returns or logs the seed token, is covered by the existing IP-keyed auth rate limiter, and rejects all attempts after an admin exists. Public admin registration remains forbidden (`AdminBootstrapController.cs`; `AdminBootstrapService.cs`; `UserRepository.CreateFirstAdminAsync`).
- **Resolved (backlog 12): license plates are encrypted once.** `DriverService` now supplies only normalized plaintext and the EF value converter is the sole encryption layer. The plate-specific converter tolerates legacy double-encrypted rows by authenticating/decrypting a detected nested ciphertext, while TOTP conversion remains unchanged. Created (but did not apply to an application database) transactional, idempotent migration `20261125085123_RemoveDoubleLicensePlateEncryption`; its `Down()` re-applies the outer layer. PostgreSQL tests cover new writes, legacy reads before/after migration, repeat migration, untouched single-layer rows, and rollback.
- **Resolved (backlog 16): car document paths and photo references are driver-scoped and server-validated.** Registration and update accept only canonical `private://` storage keys in the document-type bucket and authenticated user's folder, with strict generated filenames and JPEG/PNG extensions; URLs, traversal, encoded tricks, wrong folders, and other drivers' keys return 400. Car-photo upload now returns a canonical storage key and the server builds the stored public URL (`DriverDtos.cs`; `CarStoragePath.cs`; `DriverService.cs`; `SupabaseStorageService.cs`; `DriverController.cs`).
- **Swagger is enabled by default outside development too.** Base configuration sets `Swagger:Enable=true`, and `Program.cs` honors it regardless of environment (`appsettings.json:62-64`; `Program.cs:372-381`). This is an attack-surface/configuration risk, not an authorization bypass by itself.
- The manual liveness approval route exists despite `Rules.md:168` explicitly forbidding it (`AdminController.cs:126-130`; `AdminService.cs:292-312`). This is a requirements/security-policy contradiction that needs a decision, not dead code.

### Rides, bookings, ratings, and trust

- **Normal ride progression deadlocks at the first stop.** Arrival requires a recent GPS row, but REST/SignalR location updates are accepted only when `Ride.Status == Active`. The ride becomes Active only after that first arrival. The mobile app also starts GPS sharing only for an already Active ride. Thus a Posted ride cannot satisfy first-arrival validation through the provided flow (`DriverService.cs:614-685,834-878`; `PakiCarpoolHub.cs:90-113`; `driver_screens.dart:1131-1133,1185-1256`).
- **Booking acceptance is race-prone.** It reads the overlapping count and updates status without a transaction, lock, or conditional status update. Two drivers' requests for the same segment can both pass, and the timeout job can race acceptance as well (`DriverService.cs:404-441`; `BookingTimeoutJob.cs:44-69`). This confirms the unresolved concern noted for `SeatCapacityQuery`.
- **Bookings can be accepted on a cancelled/completed ride.** `AcceptBookingAsync` never validates `ride.Status`. Driver cancellation also changes only Accepted/Active bookings, leaving Pending bookings pending until the timeout job; they can be accepted during that window (`DriverService.cs:255-330,404-441`).
- **Rejected bookings can prevent ride completion forever.** `AreAllBookingsCompletedOrCancelledAsync` returns false for `Rejected`, so a ride with a rejected booking plus otherwise completed bookings never satisfies the completion check (`BookingRepository.cs:130-137`; `DriverService.cs:783-792`).
- **Resolved (backlog 9): passenger-to-driver rating ID mismatch.** Ride DTOs now expose `DriverUserId` (Users.Id) alongside `DriverId` (DriverProfiles.Id), and the mobile feedback screen submits the user ID as `rateeId`, which is what `RatingService` resolves (`DriverService.cs`; `PassengerService.cs`; `passenger_screens.dart`; `RatingService.cs:55-68`).
- **Resolved (backlog 10): no-show penalties can never accumulate through current flows.** No-show reports now persist a `NoShowLog` and apply the -10 penalty to the offender atomically with the booking cancellation, under participant, three-minute, and en-route guards, with one report per booking enforced by the database. At 4 no-shows an admin-review flag is raised instead of an automatic suspension (`PassengerService.cs`; `DriverService.cs`; `BookingRepository.RecordNoShowAsync`; `TrustService.cs`).
- **Stop-order validation does not enforce a contiguous sequence.** It checks uniqueness and positivity but not `Min == 1` or `1..N`, despite its error text. Gaps and a starting order greater than one are accepted (`DriverService.cs:194-225`).
- **Resolved (backlog 16): approved-car edits use a separate replacement review.** Editing an Approved car creates or updates a Pending replacement linked by `ReplacesCarId`, leaving the original Approved and unchanged. Approval transactionally marks the replacement Approved and sets the original's `ReplacedByCarId`, which excludes only the original from new-ride selection; existing Posted/Active rides are untouched. Rejection affects only the replacement (`DriverService.cs`; `AdminService.cs`; `UserRepository.ApproveDriverCarAsync`; migration `20261125124554_SecureCarReplacementUploads`, created but not applied).
- **Admin flag resolution is non-atomic.** `ActionFlagAsync` saves `ActionTaken` before applying suspension/warning and sending notifications. A later failure leaves a resolved-looking flag whose intended action was not fully applied (`AdminService.cs:479-519`).

### Maintainability, dead code, and test risk

- **Layering rules are violated:** `DriverService`, `PassengerService`, and `AdminService` directly inject/query/save `PakiCarpoolDbContext`, despite comments claiming persistence goes through repositories and `Rules.md:18,164` requiring repository-only DB access (`DriverService.cs:20-55`; `PassengerService.cs:20-51`; `AdminService.cs:22-50`).
- **Dead/unused implementation remains:** `RevokeTokenAsync` has no callers; `ReportQuery`, `RideAnalyticsQuery`, and `LiveLocationQuery` are registered but have no consumers beyond their own classes; the active hub uses its own counter rather than `ThrottledHub.IsThrottled`, leaving that base method/cleanup path unused (repository/service files; `Program.cs:69-73`; `PakiCarpoolHub.cs:90-146`; `ThrottledHub.cs:22-55`). The unused `CreateNoShowLogAsync` was removed in backlog 10.
- **Legacy duplicate login fields remain:** `FailedLoginCount`/`LockoutUntil` coexist with `LoginFailCount`/`LoginBannedUntil`; current login logic uses the latter, while the former are only initialized/reset (`User.cs:34-37`; `UserRepository.cs:205-234,321-353`; `AuthService.cs:831-869`).
- **Public API contract typo is intentional but risky:** search exposes `DeparturTime`, and Flutter depends on that exact misspelling. Renaming only one side would break departure display (`PassengerDtos.cs:33-43`; `RideSearchService.cs:67-78`; `passenger_screens.dart:697-712`).
- **No backend test projects/tests were found.** Existing Flutter tests do not exercise the API, SQL, migrations, or critical authorization/ride flows. Static code was read, but nothing was built or executed.
- No literal TODO/FIXME comments were found in the searched backend C# source. The empty `NotificationController`, `TrustController`, and `EmailController` are documented route-less shells rather than accidentally discovered TODOs.

## Database and SQL

- **Resolved (backlog 11): ride search evaluates all valid ordered stop pairs.** `RideSearchQuery` no longer limits matching to the independently nearest start/end stops. It forms every in-radius `Upcoming` pair whose drop-off follows its pickup and returns each capacity-available pair; `RideSearchService` selects the best pair per ride by match rank and combined distance (`PakiCarpool.Repository/Dapper/RideSearchQuery.cs`; `PakiCarpool.Services/Implementations/RideSearchService.cs`).
- **Resolved (backlog 11): search seat availability uses maximum per-segment occupancy.** Search and atomic acceptance share the same Pending/Accepted/Active occupying-booking SQL and count bookings on each route segment rather than summing an entire interval. A pair is searchable only when every segment has a free seat; non-overlapping subsegments therefore do not consume each other's capacity (`RideSearchQuery.cs`; `SeatCapacityQuery.cs`).
- **The “race-condition-safe” seat check is only a count query:** `SeatCapacityQuery` has no lock/transaction of its own, and no database constraint enforces per-segment capacity (`SeatCapacityQuery.cs:7-8,28-50`; `BookingConfiguration.cs`). The API acceptance path likewise performs no transaction/conditional update, so concurrent acceptance can overbook (`DriverService.cs:404-441`).
- **Case-insensitive account checks are not backed by a case-insensitive uniqueness constraint:** see the email mismatch in section 3. `EmailExistsAsync` plus a normal unique index leaves a case/race variant path (`UserRepository.cs:29-53`; `UserConfiguration.cs:19-24`).
- **Report “TotalRevenue” is not revenue from completed bookings:** it sums `Rides.Fare` once per completed ride, regardless of completed passenger count or `IsCashPaid` (`ReportQuery.cs:118-145`). With zero or multiple bookings this can understate or overstate cash fares.
- **Referential integrity is incomplete:** migrations define no foreign keys for `DriverLocations.DriverId/RideId`, `Ratings.RideId/RaterId/RateeId`, `Flags.ReporterId/ReporteeId/RideId`, `NoShowLogs.ReporterId/OffenderId/RideId`, `CancellationLogs.UserId`, or `ChatMessages.SenderId/ReceiverId` (`20260802095934_InitialCreate.cs`; corresponding configuration files). Orphaned references are possible if service checks fail.
- **Important value constraints are absent:** there is no database check for `Ratings.Stars` 1–5, positive `Rides.MaxSeats`/`Fare`, coordinate ranges, or booking stops belonging to the same ride and having pickup before drop-off. Only `DriverCars.AvailableSeats` has an explicit 1–6 check (`DriverCarConfiguration.cs:11-14`; `RatingConfiguration.cs`; `RideConfiguration.cs`; `BookingConfiguration.cs`).
- **Liveness review queue has no explicit lifecycle:** rejected and never-reviewed profiles cannot be distinguished by its query fields, so queue behavior can be wrong unless another mechanism clears photo metadata (`UserRepository.cs:415-435`).
- **No RLS/policy SQL was found in EF migrations.** Actual Supabase/PostgreSQL RLS configuration and the database role's privileges are unverified; authorization therefore cannot be assumed from the database (`PakiCarpool.Repository/Migrations`). All Dapper statements reviewed use parameters rather than interpolated SQL values.
